Plain Language Plan

LyricsLab already has the pieces of a mobile writing app: local songs, an editor WebView, selection context, and a native suggestion bar. This loop makes the suggestion bar smarter without turning the editor into a new product.

The work starts by locking scope. The MVP is not full rhyme visualization, not a chatbot, and not cloud ranking. It is a small, reliable offline feature: when the writer is drafting a lyric, the app can look at the most useful nearby word, find deterministic rhyme candidates from CMU-style pronunciations, and offer a short list that can be inserted at the caret.

Implementation then protects the editor contract before adding engine behavior. First the current suggestion and selection paths get tests. Then a pure TypeScript rhyme core is built with small fixtures. After that, the full CMU dictionary is converted into a deterministic runtime artifact so the app never parses raw dictionary text on the typing path.

Only once those layers are stable does the plan replace placeholder suggestions. The native bar stays the product surface; the smarter provider sits behind it. Final phases improve ranking, measure performance, record evidence, and file follow-up work for the bigger ideas that are intentionally outside this MVP.

The editor bridge remains narrow. This loop does not add highlight span protocols, Tiptap decorations, phrase-rhyme visualization, AI services, sync, IAP, audio, neural ranking, or teachable slant preferences unless a later product decision explicitly widens scope.

Loop Rules

These are the operating rules for the autonomous implementation loop. If Beads and this file disagree, Beads wins.

How Work Moves

  1. Select exactly one ready Beads child issue.
  2. Run the selector gate before launching implementation.
  3. Read the linked phase doc and update the matching turn doc.
  4. Launch implementation with the required scout and helper swarms.
  5. Review with thermo-nuclear-code-quality-review.
  6. Let reviewer or CI agents own gate repair when CI exists.
  7. Close the phase only after review, gates, Beads, and turn docs agree.

Hard Boundaries

  • Do not log user lyric content.
  • Do not store HTML as canonical lyric state.
  • Do not widen the WebView bridge for highlighting in this loop.
  • Do not parse full CMU data on each typing update.
  • Do not open parallel implementation PRs unless the phase says so.
  • File follow-ups instead of absorbing post-MVP work.

Autonomy Model

Most of this loop can run autonomously when the tracker and branch state are clean. The loop should pause for human input only where the work depends on unavailable device evidence, a product scope decision, broken credentials, or unresolved review and CI state.

Selector chooses the next ready issue.

Beads should currently route Phase 00. Later phases unlock one at a time.

Implementation thread owns the selected slice.

It reads the phase doc, scopes the edit, uses helper swarms, and opens one PR.

Reviewer thread owns critique and repair routing.

Review is strict, evidence-first, and recorded in the existing phase turn doc.

Closeout selector decides whether to continue.

The loop proceeds by default unless blocked, interrupted, or review/CI is unresolved.
